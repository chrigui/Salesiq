Scope

1 · Goals, non-goals, personas

Goals

  • Any tenant builds a reusable, versioned Deal Room template for any industry — insurance, real estate, automotive, or a vertical that doesn't exist yet — with zero code changes, mirroring how industry packs already work for the core recommendation engine.
  • A template is edited and published independently of any specific deal; an instantiated room is frozen to the exact template version it was built from, so a live negotiation never silently reflows.
  • Every widget is real, configurable, permission-aware, and theme-aware — no placeholder buttons, no "coming soon" states shipped as if they were live.
  • The builder works completely without an AI key configured; AI only ever enhances, never blocks or replaces a working default.

Non-goals (this phase)

  • No live e-signature vendor integration (DocuSign/HelloSign/etc.) — Signature ships with a real click-to-sign audit record, explicitly marked "not connected" to a legal e-sign provider.
  • No realtime push delivery for Chat — messages are real and persisted; delivery is polling-based until a realtime provider is chosen.
  • No arbitrary code execution in "Custom Components" — a small allow-listed set of configurable blocks only, for the same reason a multi-tenant rendering engine should never execute admin-authored code in front of another tenant's customers.
  • No product-wide i18n framework or full dashboard dark-mode — theming/localization work is scoped to the rendered Deal Room output, following the same narrow scope the Brochure module already shipped.

Constraints

2 · Architecture constraints (binding)

ConstraintRule
Reuse over rebuildThe widget registry, section-composer, theme/branding CSS-var mechanism, tenant-scoped CRUD pattern, audit wiring, and deterministic-first/AI-optional content pattern are the same machinery built for Brochures, generalized — never duplicated.
Tenant scopingEvery model carries tenantId + an index on it; natural keys are composite (@@unique([tenantId, x])), never a bare global unique — the schema's own stated convention.
Additive migrations onlyEvery schema change is verified additive (new tables/columns/enum values, never a destructive statement) before it ships, exactly as PR 1's migration was.
Immutable versioningPublishing or rolling back a template always creates a new DealRoomTemplateVersion row; nothing overwrites history.
Frozen instancesA DealRoom stores the exact templateVersionId it was created from — it never silently follows later template edits.
No fabricated functionalityAnything requiring infrastructure this project doesn't have (a paid e-sign vendor, a realtime delivery service) ships with real data models and UI, explicitly marked not-connected — never faked as working.
Epics

3 · Epics, user stories, acceptance criteria

PR 1 · Data model & schema

DONE

The reusable-template/frozen-instance split, plus every genuinely new data surface (tasks, chat, approvals, signatures) the Brochure module never needed.

As a platform engineer, I can add the Deal Room schema without touching a single existing table's data so that the migration is provably safe.
  • Acceptance criteria
  • New models only: DealRoomTemplate, DealRoomTemplateVersion, DealRoom, DealRoomAsset, DealRoomEvent, DealRoomTask, DealRoomMessage, DealRoomApprovalStep, DealRoomSignatureRequest
  • One additive enum value (Designer added to UserRole) — no destructive statement in the generated migration
  • npx prisma migrate dev applied cleanly against a real local Postgres instance; migration SQL manually reviewed
As a tenant admin, I can grant the new Designer role and Deal Room capabilities so that template-building is a real, enforced permission, not an assumption.
  • Acceptance criteria
  • Three capabilities added: dealroom-templates.manage, dealrooms.manage, dealrooms.view
  • Wired into both core/data/permissions.ts and the seed script's independent capability list in the same commit — the seed list drifting from the real one is exactly how an earlier brochures.manage seeding gap happened
Dependencies: none · Exit: clean typecheck/lint/build; reseed confirms the expected permission row count.

PR 2 · Template Builder UI

P0

Real visual drag-and-drop — the brief explicitly calls for it, so this is where a new dependency (@dnd-kit/core + @dnd-kit/sortable) is justified, unlike the Brochure Editor's up/down-arrow reuse.

As a Designer, I can create, duplicate, archive, publish, and preview a template so that the full template lifecycle is real, not partial.
  • Acceptance criteria
  • Template list view: create / duplicate / archive / publish / preview, each a real state transition against DealRoomTemplate.status
  • Duplicate copies the current published version's sections into a new Draft template — not a shallow reference
As a Designer, I can drag to reorder and toggle widgets so that layout composition is genuinely visual, keyboard-accessible, and screen-reader friendly.
  • Acceptance criteria
  • Real pointer drag-and-drop reorder via @dnd-kit; keyboard reorder works without a mouse
  • Enable/disable toggle per widget persists to the working draft version
Dependencies: PR 1 · Exit: a Designer builds a template end-to-end with zero backend changes needed.

PR 3 · Widget Library

P0

Every requested widget except Signature/Chat (deferred to PR 8, alongside their data models), each real, configurable, and honest about what it can and can't do.

As a Designer, I can add Hero, Gallery, Comparison Table, Financing/Coverage/Risk calculators, Timeline, Documents, Tasks, Approval-status, Feedback, and allow-listed Custom Components so that one engine covers insurance, real estate, or any other vertical.
  • Acceptance criteria
  • Financing/Coverage/Risk calculators use transparent, user-editable formulas — the same honest pattern the existing ROI Calculator already uses, not a fabricated actuarial model
  • Custom Components render only from a fixed, reviewed component set (stat block, callout, two-column text, spacer) — never arbitrary admin-authored code
  • Every widget respects the room's theme and the viewer's permission level
Dependencies: PR 2 (registry pattern) · Exit: every widget in the approved list (minus Signature/Chat) renders real data in at least one demo room.

PR 4 · Rendering Engine

P0

Generalizes /b/[slug] into /d/[slug], resolving a DealRoom against its frozen template version, with real public and restricted access.

As a salesperson, I can share a Deal Room link that either anyone-with-the-link can open, or that requires a per-recipient access code so that sensitive negotiation content isn't public by default.
  • Acceptance criteria
  • accessMode: PublicLink behaves like today's Brochure microsite; Restricted requires the room's real accessCode
  • SEO metadata (title/description/OG image) generated only for PublicLink rooms — a Restricted room is never indexable
  • An unpublished or archived room 404s publicly, exactly like Brochure's existing preview-gating behavior
Dependencies: PR 1, PR 3 · Exit: a real, published Deal Room renders correctly for both access modes, verified against a live server.

PR 5 · Theme & Branding Engine

P1

Extends the existing CSS-variable brand injection with real, bounded customization — never an open door to arbitrary assets.

As a Designer, I can pick a font, radius, and spacing scale, and upload a logo so that a Deal Room matches the tenant's brand without touching code.
  • Acceptance criteria
  • Font choice is an allow-listed next/font set — not arbitrary font-URL injection
  • Logo upload reuses the existing Postgres-blob asset storage pattern, size-capped
Dependencies: PR 4 · Effort: small, mostly additive to existing theme plumbing.

PR 6 · Versioning

P1

Publish, rollback, and compare — all built on the immutable version rows from PR 1.

As a Designer, I can see exactly what changed between two versions and roll back so that a bad publish is recoverable without losing history.
  • Acceptance criteria
  • Publish requires a change-reason field, stored on the new version row
  • Compare view shows added/removed/reordered widgets and changed config keys structurally, not a raw JSON diff
  • Rollback creates a new version copying an old snapshot forward — never rewrites history in place
Dependencies: PR 1, PR 2 · Exit: a rollback demo, then confirm the rolled-back version is a new row, not a mutation.

PR 7 · Permissions

P0

Full enforcement of all six roles across every Deal Room route.

As a platform admin, I can trust that every Deal Room route is capability-gated so that a Viewer can never mutate a template or room.
  • Acceptance criteria
  • Every mutating route calls requireCapability with the correct Deal Room capability, tenant-scoped via the existing updateMany-with-compound-where pattern
  • A dedicated cross-tenant isolation test, mirroring the existing Lead-route precedent
Dependencies: PR 1 (capabilities already exist) · Effort: mostly a verification pass across PRs 2–6's routes.

PR 8 · Analytics, Signature & Chat

P1

Real event capture plus the two honestly-scoped widgets whose data the analytics funnel needs to be real rather than aspirational.

As a salesperson, I can see real views, clicks, task completions, and signature status for a room so that the dashboard reflects only recorded events, never fabricated ones.
  • Acceptance criteria
  • DealRoomEvent kinds recorded on real user actions only (View, WidgetInteraction, Download, Share, ProposalAccepted, TaskCompleted, SignatureRequested, SignatureSigned)
  • Signature widget records a real click-to-sign audit entry (typed name, timestamp, IP) with a visible "not connected to a legal e-signature provider" disclosure
  • Chat persists real messages with real timestamps; delivery is polling-based, disclosed as such
Dependencies: PR 1, PR 3, PR 4 · Effort: the largest remaining PR — data-model wiring plus two full widgets.

PR 9 · AI Layout Assistant

P2

Deterministic-first suggestions that work with zero AI dependency; Claude only ever proposes a reviewable diff.

As a Designer, I can get a recommended starting widget set for a category with no AI key configured so that the builder never blocks on AI.
  • Acceptance criteria
  • A static per-category recommended-widget mapping ships with the feature — no AI call required for the baseline suggestion
  • Claude-optional suggestions (reorder rationale, missing-section flags) render as an explicit apply/reject diff — never silently overwrite existing content
Dependencies: PR 2, PR 3 · Effort: moderate; reuses the existing deterministic-first/Claude-optional AI route pattern.

PR 10 · E2E testing & production hardening

P0

Real automated coverage plus a first unit-test framework, since only Playwright e2e exists today.

As the engineering team, I can rely on CI to catch a Deal Room regression so that the feature stays production-ready as it grows.
  • Acceptance criteria
  • Playwright suite: template create → widgets → publish → room create → public render → analytics → rollback → permission-denial cases
  • Vitest added for pure-logic unit tests (version diffing, permission checks, deterministic layout suggestions) — the standard lightweight pairing alongside the existing e2e suite, not a second heavyweight e2e runner
  • Final clean typecheck/lint/build; manual pass — light theme, mobile + desktop, keyboard-only navigation
Dependencies: PRs 1–9 · Exit: green CI on the full suite; sign-off that nothing in the plan was silently descoped without disclosure.
